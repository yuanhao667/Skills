# 协作与生产流程

## 1. 选题入口

### 用户给出产品

先做快速判断，不超过一屏：

- 小红书潜力：高 / 中 / 低，并写一句原因。
- 公众号潜力：高 / 中 / 低，并写一句原因。
- 时机：抢先机，或后发差异化。
- 建议角度：只给 1–2 个。
- 下一步：是否值得下载安装与实测。

这时不要做完整产品分析，不要预写 7 页，不要输出几千字。

### 用户没有产品

推荐 3–4 个当下有流量机会的候选。每个候选只包含：

1. 产品是什么。
2. 为什么现在值得关注。
3. 可以从什么特别角度讲。
4. 竞品或其他创作者主要在讲什么。

最后明确推荐一个，并说明推荐理由。软件、Skill、AI 工具占大多数；硬件少量推荐，优先用户已经购买或明确愿意购买的新品。

## 2. 选题原则

- AI 产品为主，但账号不做成只有 AI 的垂直资讯号。
- 产品可包含软件、Skill、服务和少量新硬件。
- 兼顾流量价值与用户借持续输出探索新工具的个人目标。
- 能抢先机时优先抢先机。
- 已经被大量讨论时，寻找后发优势：反常识体验、真实失败、具体场景、竞品少讲的边界、长期使用摩擦。
- 不做纯资讯播报，不靠罗列功能撑内容。

## 3. 官方资料核验

在建议测试前，优先查看：

- 官方首页与核心定位。
- 官方文档、帮助中心和 FAQ。
- Changelog、Release、博客或发布帖。
- 定价、平台限制和账号要求。
- 官方演示中反复强调的差异点。

把官方宣称转成可验证任务。例如官方强调“任务不中断”，就安排人工接管、改变页面状态、再交还 Agent 的恢复测试。

## 4. 五分钟体验引导

一次最多给 3 个任务。每个任务都说明：

- 做什么。
- 中途故意改变什么。
- 观察什么。
- 需要记住或截下什么证据。

优先观察：

- 第一次使用能否找到入口。
- 官方主卖点是否真的可感知。
- 中断、接管、交还、恢复是否可靠。
- 人和 Agent 是否互相抢操作权。
- 登录态、权限和数据是否按承诺复用。
- 与旧产品并存时是否让用户迷路。
- 出错后是自恢复、重读状态、走回旧路径还是卡住。

用户时间有限时，宁可做一个带干扰变量的真实任务，也不做十个浅尝辄止的功能打卡。

## 5. 接收用户输入

允许用户想到什么说什么。内部把内容整理为：

- 事实与截图证据。
- 用户亲测感受。
- 官方宣称。
- 合理推断。
- 尚未确认的问题。

不要要求用户先写成完整评测。发现特别有价值但未验证的点时，只补一个最小测试。

## 6. 轻量拆解闸门

只有选题确定且已有基本体验后，才进入轻量拆解。默认输出：

- 核心价值一句话。
- 精简用户旅程。
- 能确认的产品架构或 Agent 关系。
- 2–3 个亮点。
- 1 个意外发现。
- 集中到一页的问题与边界。
- 最终建议。

未知的后台机制明确写“未知”，不猜模型、数据库、记忆实现或调度方式。

## 7. 八张画板蓝图闸门

先列出页面职责与每页唯一判断，得到用户确认后再做 Figma。每次固定生成完整 8 张画板：

1. 产品推荐封面。
2. 使用亮点。
3. 实际怎么用。
4. 产品怎么工作。
5. 我的意外发现。
6. 用下来有哪些问题。
7. 最终建议。
8. 小红书 & 微信小绿书发布标题与正文。

01–07 是发布图片，08 是文案复制区、不导出。页名必须直接写职责名，不用模糊的 “Page 1” 或旧项目临时名；缺少任意一张均不算完整交付。

## 8. 设计迭代方式

- 用户指出当前问题时，先修当前页，再把可复用结论写回视觉规范。
- 不在原版上直接覆盖；复制整套到日期页下方做 V2、V3。
- 一轮只围绕一个主方向改，避免同时换文案、结构、颜色和截图导致无法判断。
- 用户已经手工调整时，先重新读取当前 Figma 状态，以用户最新版本为准。
- 任何肉眼可见的缺陷都要沉淀为规则，避免下一页重复犯错。

## 9. 微信分支

小红书完成后，若用户要微信版本，默认把同一套 7 张 3:4 图直接用于公众号图片消息（小绿书 / 贴图），并复用第 8 页短正文；去掉小红书话题标签即可。只有用户明确要求公众号长文章时才扩写，并遵循 [wechat-conversion.md](wechat-conversion.md)。
